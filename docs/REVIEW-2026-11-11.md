## Result in one paragraph

The mirror is not a kernel. The engineering tree is a Ginux patch profile plus ThoxOS userspace. The documented `scripts/build-native.sh` on public `334539c` fails because `thox-registry-anchor.patch` compiles a certificate the script never installs. Applying `patches/thox-ai/thoxinux/0001-build-and-launcher.patch` produced a 12,507,648-byte `GINUX.EFI` that reached the `ginux>` prompt under QEMU. The published v0.9.1 EFI (`1bc1c7af...`) also reached that prompt. Neither boot ran the 22-command lifecycle. The local EFI hash does not match the published EFI. Apache-2.0 READMEs and the GPL-2.0-only linux-thox README each carry a footer that forbids copying. Those footer and link fixes are patches, not pushes, because this run cannot write to Thox-ai.

## Claims versus the code

The mirror README said this repository is a Rust-first, Linux-ABI-compatible kernel, and that the public home would be Thox-ai/thoxinux once created. The org repository has existed since 2026-10-31 and is public. This tree had no LICENSE, no NOTICE, and no source. The README in this PR says that.

Thox-ai/thoxinux README calls the project a hardened Ginux fork that boots as one EFI image with no host kernel underneath. What is in git is four patches, a launcher, a Debian/QEMU userspace, and an agent supervisor. The kernel Rust sources are downloaded at build time. There is no `*.rs` file under `kernel/`. The 15 Rust files are all in `userspace/agentos/`. The identity patch prints an engineering-preview line and says physical hardware is unvalidated. "Hardened" and "no host kernel underneath" overshoot the tree. The desktop images boot a Debian kernel. Ginux runs under QEMU.

The same README said the repository is private and that v0.9.0 is a draft waiting on a founder order. `v0.9.0` and `v0.9.1` are published prereleases. v0.9.1's tag commit is `84b4a7e740496297ca79dff735834ca2a8f2bad3`. Current main `334539c` is a later docs merge. The banner in the EFI is still `ThoxInux 0.9.0`. `kernel/ginux/README.md` and `write-build-receipt.py` still say `0.2.0-azure-candidate` and cite EFI `3ebcc904...`, which the reconciliation note already calls the pre-consolidation candidate.

linux-thox README line 5 said it is the kernel shipping ThoxOS Core devices run. The status section under that says v0.1.0 is packaging only, the patch series is empty, and the build was not executed. `tools/build-linux-thox.sh` was mode `100644`, so `./tools/build-linux-thox.sh` cannot start. `git log v6.6..HEAD` cannot run: the only tag found by `git ls-remote --tags` on that repo during release inspection is `v0.1.0`. kernel.org on this date still published the pinned tarballs. ## Reuse toward a Rust ThoxOS kernel and a protection POC

What is actually implemented, and worth keeping:

- A preparer that refuses a dirty Ginux checkout and applies one ordered series (`prepare_source.py`). The four patches are small: stack and socket fixes, a banner, QEMU OVMF file names plus `aw-bits=48` when QEMU advertises it, and one extra TLS root for `registry.thoxos.internal`.
- A QEMU launcher that checks SHA-256, refuses root, caps the guest at 2 GiB, and does not pass host disks or GPU.
- An ed25519 token, an append-only audit log, and a deny-by-default broker for `fs.read`, `fs.write`, `exec`, and `net.http_get` (`userspace/agentos`).
- A clean-room spec (`thox-kernel-lab`) for a `no_std` kernel where an agent exists only through a create syscall with a closed capability set, and where Linux compatibility is a userspace shim rather than the kernel personality. That spec is not code.
- An empty linux-thox series and KSPP-style config fragments (dm-verity on the device classes, zram, schedutil). That is a Linux packaging sketch, not the Rust kernel.

What a true in-tree Rust kernel still requires: vendor or subtree Ginux at the pin (or a later one), keep THOX changes as patches or a real fork, and stop describing the Debian guest as that kernel. The startup patch is the only kernel behavior change. Identity, firmware file names, and one TLS root are not a new kernel. `docs/COMPATIBILITY.md` scores the upstream syscall ledger at the pin and says those calls were not re-tested in this tree.

What a protection POC still requires: enforcement outside the agent process. Today a valid token starts a normal process. The broker cannot see a program that never calls it. The basename exec rule and the time-based signing fallback should be decisions before that POC claims confinement. The lab spec's create-syscall capability set is the shape that would match the product sentence. The Ginux domain controller is the piece that could host it, and this review only showed that the controller prompt appears. The boot catalog line about a development-only RFC test key means Secure Boot for the EFI is not done.

ThoxKey, ThoxAir, ThoxMini, and ThoxClip do not appear as board targets in this family. linux-thox names E2, P4, and P6 as arm64 classes and desktop as x86-64, with no device tree and no image. Nothing here is a firmware image for a USB key or a clip-on device.
